# revokd

세션 단위 접근 철회를 VPN 게이트웨이 데이터 경로까지 실시간으로 전파하는 Go 구현. 유출이 의심되는 세션의 새 연결과 이미 열린 연결을 함께 끊고, Active-Active 게이트웨이 전체의 적용을 ACK로 확인합니다.

현재 버전은 TCP 중계 게이트웨이에서 집행하는 프로토타입이며, Go 표준 라이브러리만 사용합니다.

## 배경

AI를 활용해 취약점에 접근하는 공격으로 대규모 개인정보 유출 사례가 늘어나면서, 이상 징후를 관찰하는 즉시 접근을 끊을 수 있는 구조가 필요하다고 판단해 만들었습니다. 인증 토큰을 만료시키거나 철회해도 이미 열린 터널과 연결은 바로 끊기지 않습니다. 이 프로토타입은 탐지 결과를 별도의 인증된 제어 채널로 게이트웨이에 보내, 새 연결과 이미 열린 연결을 함께 차단합니다.

## 측정 결과

단일 호스트, loopback TCP, 게이트웨이 2대(Active-Active), 30회 반복. 유출 세션은 20 MB/s로 내려받고, 같은 시간에 정상 세션이 512 KB/s로 내려받습니다. 탐지 기준은 2초 안에 5 MB입니다.

| 지표 | 보고 주기 50ms | 보고 주기 10ms |
|---|---|---|
| 탐지 → 두 게이트웨이 ACK (p50 / p95) | 0.22 / 0.43 ms | 0.18 / 0.28 ms |
| 기준 초과 → 연결 차단 (p50 / p95) | 27.8 / 46.6 ms | 6.2 / 10.7 ms |
| 기준 초과 후 추가로 넘어간 데이터 (p50 / p95) | 0.55 / 0.94 MB | 0.12 / 0.20 MB |
| 차단 후 다른 게이트웨이로 재접속 | 30/30 거부 | 30/30 거부 |
| 정상 세션 오탐 | 0건 | 0건 |

차단 지연의 대부분은 게이트웨이가 사용량을 보고하는 주기입니다. 제어 채널로 철회를 전파하고 ACK를 받는 데는 1ms 미만이 걸립니다. 보고 주기를 줄이면 추가 유출량이 줄지만 제어 채널 트래픽이 늘어나는 트레이드오프가 있습니다. 원본 데이터는 `bench/` 폴더에 있습니다. `go run ./cmd/demo`를 실행하면 감사 로그(`audit.log`)가 함께 생성됩니다.

loopback 측정이라 실제 네트워크 지연은 포함되지 않았습니다. 실제 환경에서는 게이트웨이와 제어 서비스 사이 RTT만큼 늘어납니다.

## 구조

```
client --(data)--> gw-a --+--> upstream (보호 리소스)
client --(data)--> gw-b --+
gw-a, gw-b <--(제어 채널, HMAC 서명)--> control plane (탐지기)
```

| 패키지 | 역할 |
|---|---|
| `internal/control` | 제어 채널. 모든 메시지를 HMAC-SHA256으로 서명하고, 메시지 종류까지 서명에 포함해 다른 종류로 재사용하지 못하게 함 |
| `internal/policy` | 게이트웨이의 세션 정책 상태. 이벤트 ID로 중복을 무시하고, 세션별 단조 증가 epoch로 늦게 도착한 옛 이벤트가 새 결정을 덮지 못하게 함 |
| `internal/gateway` | 데이터 경로. 세션별 연결(flow)과 전송량을 추적하고, 철회를 받으면 기존 연결을 닫은 뒤 ACK. 제어 채널 lease가 끊기면 새 연결을 거부(fail-closed) |
| `internal/controlplane` | 모든 게이트웨이의 사용량을 합산해 슬라이딩 윈도우로 탐지하고, 철회 이벤트를 전 게이트웨이에 보내 ACK를 모음. 감사 로그 기록 |
| `cmd/demo` | 전체 시스템을 띄워 반복 측정 |

## 설계 판단

- **세션 단위 철회 + 게이트웨이 집행**: 토큰 만료만으로는 열린 연결이 남고, WireGuard peer 제거는 사용자 전체 접속을 끊습니다. 세션 단위로 철회하고 게이트웨이가 해당 세션의 연결만 닫습니다.
- **게이트웨이 사용량 합산**: Active-Active에서 트래픽을 여러 게이트웨이로 나눠 탐지를 피하지 못하도록 세션별 사용량을 게이트웨이 전체에서 합산합니다.
- **집행 후 ACK**: 게이트웨이는 연결을 실제로 닫은 다음 ACK를 보냅니다. ACK가 오지 않은 게이트웨이는 `Pending()`으로 확인할 수 있습니다.
- **제어 채널 단절 시 fail-closed**: 철회를 받을 수 없는 게이트웨이는 새 연결을 받지 않습니다. 가용성보다 유출 방지를 우선하는 선택이며, 실제 운영에서는 리소스 민감도별로 다르게 둘 수 있습니다.

## 테스트

```
go test -race ./...
go run ./cmd/demo -trials 30
```

| 테스트 | 검증 내용 |
|---|---|
| 수동 철회 시 두 게이트웨이의 기존 연결 차단 | 같은 세션이 gw-a, gw-b에 연결을 가진 상태에서 둘 다 끊기고 두 ACK 모두 `applied` |
| 철회 후 재접속 거부 | 두 게이트웨이 모두 `revoked`로 거부 |
| 대량 전송 자동 철회 | 기준 초과 시 자동 철회 및 연결 차단 |
| 정상 트래픽 미차단 | 기준 이하 세션은 끊기지 않음 |
| 중복 이벤트 | 같은 이벤트 재전송 시 `duplicate`로 ACK, 상태 변화 없음 |
| 순서 역전 | 늦게 온 옛 restore가 새 revoke를 되돌리지 못함 |
| 위조 메시지 | 페이로드 변조, 메시지 종류 변조, 다른 키 모두 거부 |
| 제어 채널 단절 | lease 만료 후 새 연결 `control-lease-expired`로 거부 |

## 한계

- **실제 VPN이 아닙니다.** WireGuard 터널 대신 TCP 중계 게이트웨이에서 집행합니다. 실제 WireGuard 게이트웨이에서는 `killSession`을 peer 제거(wgctrl), nftables로 터널 IP 차단, conntrack 항목 삭제로 바꾸면 됩니다. root 권한과 리눅스 커널이 필요해 이 저장소에서는 구현하지 않았습니다.
- 탐지는 전송량 기준 하나만 씁니다. 실제로는 목적지, 리소스 민감도, 기기 상태 등을 함께 봐야 합니다.
- 이미 전달된 데이터는 회수할 수 없습니다. 차단은 탐지 이후의 추가 전송을 막습니다.
- 세션 토큰은 HMAC으로 단순화했습니다. 실제로는 IdP가 발급한 짧은 수명의 토큰을 씁니다.

## 기존 기술과의 관계

같은 문제를 다루는 표준과 제품이 이미 있습니다. OpenID의 CAEP(Continuous Access Evaluation Profile)는 IdP가 `session-revoked` 같은 이벤트를 서비스에 푸시하는 표준이고, Microsoft Entra의 CAE, Okta, Google Workspace가 이를 지원합니다. Cloudflare Zero Trust도 사용자 세션과 WARP 기기 등록을 철회하는 API를 제공합니다.

이 프로토타입은 그 아이디어를 새로 만든 것이 아니라, 같은 원칙을 VPN 게이트웨이의 데이터 경로까지 내려서 "이미 열린 연결을 실제로 끊고, 모든 게이트웨이의 적용을 확인한다"는 부분을 직접 구현하고 측정한 것입니다. 이벤트 형식(subject, 이벤트 ID, 발행 시각)도 CAEP의 session-revoked를 참고했습니다.
